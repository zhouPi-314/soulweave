# 三个许可证对比（供你选择）

> 只列会影响你的条款。三份都是 OSI 认可的开源许可，都能用于商业项目。

## 一句话版本

| | MIT | Apache-2.0 | AGPL-3.0 |
|---|---|---|---|
| 本质 | 随便用，署名就行 | 随便用，署名 + 专利授权 + 改动声明 | 随便用，但**改了且对外提供服务就必须开源** |
| 长度 | 一页 | 三页 | 十几页 |
| 别人能闭源分发你的代码吗 | 能 | 能 | **不能**（分发或提供网络服务都触发） |

## 逐项对比

| 维度 | MIT | Apache-2.0 | AGPL-3.0 |
|---|---|---|---|
| 商用 | ✅ 允许 | ✅ 允许 | ✅ 允许 |
| 修改 | ✅ 允许 | ✅ 允许（需标注修改） | ✅ 允许（衍生作品必须 AGPL） |
| 再分发 | ✅ 允许 | ✅ 允许 | ✅ 允许（必须同样 AGPL） |
| 闭源二次开发 | ✅ 可以 | ✅ 可以 | ❌ 不可以 |
| 专利授权 | ❌ 未涉及（默认无授权） | ✅ 明确授予 | ✅ 明确授予 |
| 商标授权 | ❌ 不含 | ❌ 不含 | ❌ 不含 |
| 必须保留版权声明 | ✅ | ✅ | ✅ |
| 必须附许可全文 | ✅ | ✅ | ✅ |
| 必须声明修改 | ❌ | ✅ | ✅ |
| 网络服务触发开源（SaaS 条款） | ❌ | ❌ | ✅ **第 13 条** |
| 与 GPL 兼容 | ✅ | ✅ | ✅（本身是 GPL 系） |
| 企业采用阻力 | 最低 | 中（法务熟悉，通常可接受） | **高**（很多公司直接禁止 AGPL） |

## 对你这个项目的具体影响

### 选 MIT

- 别人可以拿你的代码做成闭源产品卖，不需要给你任何回报（只需保留版权行）。
- **风险**：如果哪天你想靠"源码可见"做差异化，这个选项让差异化为零。
- 好处：传播最快，社区最友好，你自己后续闭源某些模块也不冲突（因为你是版权方）。

### 选 Apache-2.0

- 比 MIT 多两层保护：**专利授权**（贡献者不能事后拿专利告你）+ **修改声明**（别人改了什么要写出来）。
- 要求随分发保留 NOTICE 文件——你已经有 NOTICE，正好用得上。
- 好处：企业用户最愿意接受；对"可能有专利的技术"更安全。
- 代价：文件更长，部分个人开发者嫌麻烦。

### 选 AGPL-3.0

- 想防止"有人拿你的代码做个云服务卖钱却不回馈"时才有意义。
- 但你这个是**桌面应用**，不是 SaaS——AGPL 的核心条款（第 13 条网络服务）几乎用不上，
  真正生效的是"分发即必须开源衍生作品"。
- **代价**：很多公司内部政策直接禁止 AGPL 依赖，会挡住一部分使用者；
  而且你一旦引入 AGPL 代码，未来想改协议几乎没有退路（版权分散在贡献者手里）。

## 我的建议

**Apache-2.0**（如果你想长期做得正规）或 **MIT**（如果你想最低摩擦）。

- 你的差异化不在代码保密，而在角色、记忆与素材——所以不需要靠 AGPL 保护。
- 素材（模型权重、Live2D、音色）本来就要独立授权（D59.06），代码用什么许可都改变不了这点。
- 如果未来要商业化，Apache-2.0 的专利条款对企业客户更友好，也能省掉一些尽调问题。

## 你需要做的

从三个里选一个（或告诉我"用 X + 例外条款"），我会：

1. 写 `LICENSE` 全文；
2. 把 `docs/licensing/assets.json` 的 `code-app` 标为已批准；
3. 在 `NOTICE`、官网「关于」页、README 同步许可证名称与链接；
4. 重跑 `npm run license:gate`，让这一项从 FAIL 变 PASS。
